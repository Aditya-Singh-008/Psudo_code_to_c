PROJECT PROGRESS DESCRIPTION

Project Abstract
Our project translates a formally-defined, English-like pseudocode language into executable program code. Unlike informal pseudocode sketches, our input is treated as a real language with a lexer, parser, and an Abstract Syntax Tree (AST). Using a Flex + Bison compiler pipeline, we tokenize and parse pseudocode into an AST, then traverse that AST to generate well-formatted output programs. In Phase 3 we expanded beyond only C: the same AST can now target multiple output languages (C, Python, and Java) by switching only the code-generation module. We also extended the language to support integer arrays (static arrays, arrays initialized with literal values, and dynamic arrays). The system is exposed through a browser UI and a Node.js/Express backend that invokes the compiler and returns generated code and diagnostics, making the tool useful for both learning compiler design and helping beginners convert algorithms into working code.

Updated Project Approach and Architecture
The architecture follows a modular compiler design:
(1) Lexical & Syntax Layer (Flex + Bison): `logic/lexer.l` tokenizes keywords, identifiers, literals, and operators; `logic/parser.y` applies an LALR grammar to build the AST.
(2) Semantic Layer (Symbol Table): `logic/symtab.c` tracks identifiers and types (including `int[]` / dynamic arrays) and helps detect duplicate declarations; codegen emits warnings for undeclared identifiers.
(3) Synthesis Layer (Multi-target codegen): separate emitters generate different target languages: `logic/codegen_c.c`, `logic/codegen_python.c`, `logic/codegen_java.c`. `logic/main.c` selects the target language via CLI arg (`c` default, `python`, `java`).
End-to-end flow: Frontend (`index.html`, `script.js`) POSTs pseudocode + optional `lang` to the backend (`server/api/api.js`). The backend writes input to disk and runs `logic/my_compiler <lang>`, then returns generated output and any warnings/errors (stderr).

Challenges/Roadblocks
Key challenges included: extending the grammar cleanly to support multiple array forms (static, literal-initialized, dynamic) without breaking existing constructs; ensuring AST node design stays generic enough to support multiple output targets; and keeping the Windows + WSL compiler execution reliable (path conversion, stdin/stdout piping, and capturing stderr diagnostics). Another recurring challenge was maintaining consistent semantics across code generators so the same pseudocode behavior is preserved in C, Python, and Java outputs.

Project Outcome/Deliverables
Deliverables include: (1) a formally defined pseudocode language with arrays and core control-flow constructs, (2) a working compiler pipeline (Flex + Bison + C) that builds an AST, (3) multi-target code generation producing C / Python / Java source code from the same pseudocode input, (4) a browser-based frontend + Express backend for running translations, and (5) diagnostic reporting for common semantic issues (duplicate/undeclared identifiers).
